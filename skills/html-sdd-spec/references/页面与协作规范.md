# 页面与协作规范

只在设计页面、维护排期或多人协作时读取对应段落。

## 让用户看清下一步

维护 `metadata.status` 的真实工作状态，区分方案对齐、编码、验证和上线；不能因为 `codingReady=false` 就回写为“方案待对齐”。整体编码条件集中展示，子需求保留自身状态和验收。

先查现有代码和证据，再分类 `questions[].requiresUserDecision`：true 为确需用户决定的业务事项，false 为 AI 继续核实，缺省为待分类。已解决/取消的问题及时更新状态；未分类不能默认成“无需用户决定”。摘要栏展示待决策数量，弹层最多先显示三项，其余及技术核实按需展开。不因页面精简删除问题，也不代替用户确认。

默认页面采用冷白＋墨蓝，正文 16px、表格与菜单文字以清晰阅读为先，分类标题大于子项；文字保持足够对比度。语义状态色独立于主题，不能把主题蓝当作完成色。调整布局时不要靠缩小字体容纳内容。

## 六个阅读入口

- **需求**：目标、范围、验收标准和关联记录；
- **排期**：宽屏整页表格，固定八列：序号、优先级、模块/任务、关联需求、执行人、预计完成、状态、备注。点击任务名展开详情，关联需求显示名称并可跳转。备注合并进展、补充说明和阻塞原因，阻塞原因优先、重复文字去重；状态只显示统一短枚举。预计完成只读取 end 的有效 YYYY-MM-DD 日期，未确定显示“待定”，旧的条件说明保留在详情。负责人、审核人、开始时间、子任务、依赖、范围和验收结果放详情；批次、预估选填，不要求凑内容。仅精简展示，不删除事实源字段。同一模块使用同一行色；
- **接口**：按业务分组，右侧一次只看一个接口；区分新增、原有变更/复用；显式维护 `developmentStatus`（已完成/部分完成/未开发，缺省待核实），`status` 保留范围/部署说明；展示参数与默认展开的请求/响应实例；
- **数据表**：按业务分组，右侧一次只看一张表；必须区分新增、存量变更和复用，开发状态与部署说明分开；标题显示英文表名（中文名），下方直接展示默认展开的 DDL 黑色文本框；
- **架构设计**：技术方案用结论、当前现状、关键设计、影响范围、风险/待确认；架构图和时序图可使用 `diagramEngine=mermaid`、内联 SVG 或文字回退，必须保留图源或文字降级说明；
- **上线需要配置**：只列本阶段确需执行的环境变量、Apollo、DDL 和人工项；配置/SQL 文件是执行源，可用 `source` 标记路径，`content` 是阅读快照。未开发能力的配置建议留在方案，不混入发布清单。

分类可以为空。未涉及写明“不适用”及原因，未梳理完成写“待补充”和问题；不要为了填满页面虚构接口、表或架构图。

## Agent 协作

默认自动选择单 Agent 或多 Agent：小改动、单模块和无接口/数据影响使用单 Agent；跨模块、接口和数据同时变化、可并行或需要独立复核时使用多 Agent。用户明确指定时服从用户。

- 一份 SDD 只有一个负责人 Agent，负责和用户对齐、维护事实源、分派和汇报；
- 每个 PLAN 有一个主审核人和一个主执行人，可增加协作审核人/执行人；并行执行必须填写不重叠的 `ownerPaths`；
- 顺序固定为：负责人建基线 → 审核人拆解并冻结契约 → 负责人确认 `codingReady` → 执行人开发/验证 → 审核人复核 → 负责人汇报；
- 每个 Agent 读取同一份 JSON，按 `requirementIds`、`related` 和 ID 精确取数；完成后回填 `progress`、`evidence`、`changedPaths`、`blocker` 和 `next`。

## 排期状态

`plans[].status` 只能使用固定枚举：

`待拆分`、`待确认`、`编码 READY`、`待开始`、`进行中`、`待接入`、`待执行`、`待复核`、`待验收`、`阻塞`、`已完成`、`已取消`

页面为这些状态统一颜色；`plans[].note` 写补充说明，`blocker` 写阻塞原因。没有新证据时保留原状态并汇报“无变化”，不能凭感觉标记完成。

## 目录与排期交互

接口/表支持开发状态和变更类型组合筛选，分类独立保留、可恢复全部；不从自由文本猜开发完成度。目录统一为名称、可选路径、底部标签行；标签按类型/方法、变更类型、状态排列。长名称/path单行省略并悬停看全文，DOM 保留完整路径供原生 Cmd+F / Ctrl+F。页头状态仅一份，版本/编码条件用不推高正文的摘要弹层；保持清晰字号。

排期支持状态筛选、优先级高/低和序号排序、按模块归类及恢复默认。`plans[].sequence` 为唯一正整数序号，分派后保持稳定，不随筛选/排序重新编号；旧数据缺省按原数组顺序分配未占用序号，建议录入事实源固定。模块归类默认开启，模块按排序后首个任务排列，模块内按所选规则排序，同模块始终同色。

证据优先在 JSON 中保留简短结果、提交或 CI 链接。只有必要的本地材料才按需放入证据/或证据索引/，先写入项目 .gitignore，不提交材料。不要把他人无法访问的本地路径当成共享验收已完成的依据；已跟踪的历史证据单独评估迁移，不能擅自删除。

## 公共定义与字段职责

公共参数写入 `definitions.fields`（单个具名字段或字段数组），公共约束写入 `definitions.rules`（字符串或字符串数组）。接口 `request` / `response` / `rules` 中用纯 `{"$ref":"#/definitions/fields/名称"}` 或 rules 引用，原位展开，不支持覆盖和定义互引。保留每个字段的中文说明、枚举和示例；不同位置/类型/必填性不能合并。名称含 ~、/ 时按 ~0、~1 转义。例子中的 $ref 是业务数据，不解析。

`summary` 只写用途，`current` 写已核实现状，`rules` 写约束与例外，`progress` 写最近进度，`note` 只补充，`evidenceIds` 指向证据。不把同一段权限/响应包规则复制进每个接口。优先用 `html-sdd reuse <JSON>` 预览，`--output <候选.json>` 保存；确认展开合同一致再替换，兼容旧内联写法。引用格式须使用支持它的新 CLI/模板，不自动更新全局安装。不要为了缩短页面删状态维度、参数或有效约束。

## 统一状态

所有板块状态子集和颜色取自包内 `assets/statuses.json`，用 `html-sdd statuses --section <板块>` 查可选项。新文档 `metadata.statusPolicy=strict`，status 为短枚举、statusNote 为说明；验收项用 acceptance 子集。未知/跨板块值禁止；旧文档 legacy 的长句保留为说明并显示灰色待核实，不猜色。原生命周期 state、编码条件、开发状态与部署验收分开；复核状态不能随文案简化消失。

## 架构模块与当前方案

左侧 group 与需求/排期主模块对应，跨模块共性集中在整体设计。每模块默认一份主方案，加必要架构/时序图；图跟随所属模块。不要按接口或变更批次拆成碎片。正文保留采用的设计、已核实现状、关键机制、影响与未解决边界；细参数、DDL和上线配置只链接对应板块。

用户调整方案或新结论明确替代旧方案时，原位替换或合并，不保留“首轮/查漏/补充/已实现切片”等流水账菜单。复用稳定主ID，其他当前记录的旧关联迁移到合并后的ID。保留有效权限、并发、幂等、失败与生命周期约束；不把尚未落地的设计说成现状。历史只在需要追溯时读取，不强制每需求生成新的历史目录或记录。

## 让人容易读懂

先说“怎么做、为什么、现在做到哪、还差什么”。一句一件事，优先少量短要点；内容多就分到对应板块，不把细节全塞进摘要。避免连用缩写、类名和抽象名词。必要术语首次解释，准确的字段名、路径、枚举、DDL和配置不改写。

- “原子提交”→“一起保存，失败一起撤销”。
- “幂等重放”→“同一个请求重复提交，不重复创建”。
- “签名高水位”→“已发下载链接的最晚到期时间”。
- “源删除不追溯影响已发送快照”→“原文件删了，已发到聊天的副本不受影响”。

具体解释必须符合本项目实际语义，不能机械替换词语。保留权限、数量、时限、并发与失败规则，不把准确说明改成“基本可用”“已经搞定”。汇报默认300字内；页面结论先一两句，细节按需看。

右侧单项内容只显示一个主标题，编号、方法/路径和状态集中在同一头部；不叠加同名页面标题、分类小字和通用引导语。接口说明与名称完全相同则省略，独有说明与参数继续保留。

HTML 标签页标题格式为 `HTML SDD Spec <需求名称>`，需求名称取自 `metadata.title`。关联编号属于辅助信息，使用11–12px、普通字重和次要文字色；状态与参数保持原字号和语义色。

数据表可选 displayName 保存简短中文表名，与英文 name 组合为“英文表名（中文表名）”。右侧保留名称、变更/开发标签和 DDL，去掉状态、用途和差异说明区块；原字段仍保留在事实源供 AI 核对，不从长用途文字猜表名。
