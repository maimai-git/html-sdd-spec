# HTML SDD Spec

用户只需说“用 HTML SDD 实现这个需求”。自行检查项目并梳理要点，不要求用户填写接口、表和 Agent 提示词。

## 工作主线

1. 读取项目规则，记录仓库、分支、完整 SHA、检查时间/时区及未提交状态；按本次范围核实代码、路由、存储、迁移、配置和测试。明确区分现状、方案与待核实；前端默认只读。
2. 按「接续已有需求」判断应沿用还是新建 SDD，再在项目根目录维护 `html-sdd-spec/<中文开发需求目录>/方案事实源.json`，生成 `方案对齐.html`。一次开发可包含多个子需求，统一页面；目录/文档名使用中文，可夹英文，脚本除外。分类未涉及写原因，待梳理写待补充，不虚构内容。
3. 使用稳定 ID 关联需求、排期、接口、表、架构、配置。只有业务、权限、契约、迁移、外部接入或执行授权确需用户决定时提问；技术核实自己继续做。问题的 `requiresUserDecision`：true 用户决定，false AI 核实，缺省待分类。
4. 编辑 JSON 后运行 `check`、`render`，必要时 `diff`；不手改生成 HTML。方案变化先更新受影响记录；原契约不再成立时将相关 PLAN 置“待复核”、`codingReady=false`，重新评审后继续。
5. 按证据维护排期状态、进展、阻塞、下一步及验收结果。`metadata.status` 表示实际阶段，不能由编码条件倒推。代码完成、迁移文件存在不代表数据库已执行或上线验收通过。

共享事实源用仓库名或 Git URL 标识仓库，仓内文件用仓库根目录相对路径，外部资料用可访问链接，仅本机可见的资料标注「本机留存」。接手时先核对当前仓库、提交和环境，再沿用历史结论。处理 \`check\` 的 \`LOCAL_MACHINE_PATH\` 提醒时，保留证据编号、环境和验证结果。

## 从一句需求到测试

核对代码、现有测试和用户决定。先用短句复述期望结果、本期边界和当前行为。只问会改变交付的未知项，给推荐、影响和是否阻塞。已确认的规则引用原决定。

把关键边界写为 `requirements[].acceptance` 中的「前提、动作、预期」，使用稳定验收编号。等价例子可沿用已有决定；有新增规则先确认。按验收例子写测试并回填 `evidence[]`。已有功能补回归；新行为先验证测试确实能捕获失败。只报告实际运行过的环境和结果。

## 上线清单

配置文件放需求目录的 `上线配置清单/`，SQL 固定放 `上线SQL清单/上线SQL.sql`，按需创建。只登记本期分支新增且上线不可缺的配置。核对目标环境已有配置，每项填写本地实测的非敏感生效值，无法核实时填非敏感示例并标「示例值」。发布人按目标环境核对后提交工单。正式发布项在事实源只写 `configs[].source`，使用仓库根目录相对路径。正文维护在发布文件里，HTML 展示可点击的仓库相对路径，正文在正式文件里查看和修改。没有正式文件的草稿按需用 `content`。

配置和 SQL 按需各留一个文件。配置文件固定为 `上线配置清单/上线配置.properties`，新增项追加到同一文件。每项 `key=value` 上方单独用 `#` 写中文名称、用途、默认值和值的来源。默认值为空写「空字符串」，没有默认值写「无默认值」。项间空一行。把说明写进文件顶部注释，先写交什么、交到哪里，再写前提、选哪段、提交顺序和验收。用短句和可搜索的段名。如有专属使用说明，可直接链接两个文件。

配置按服务和配置位置分段。Apollo 写目标环境、AppId 和 namespace，环境变量写部署位置。SQL 按目标实例和库分段，写环境、数据库类型、实例、库名、schema 和前置依赖。单一目标也写段头；缺证据的目标位置写「待核对」，工单按段取用。

准备提交工单时运行 `html-sdd check <JSON> --release`。根据文件和行号解决缺失目标、示例值、文件不可读和旧副本过期等问题。日常草稿继续用普通 `check`。

## 接续已有需求

`init` 默认生成事实源、HTML 和 Git 忽略规则。只有专属操作确实需要独立说明时才创建 `使用说明.md`。

- 原需求仍在交付或验收中，同一目标下的补漏、修复和方案调整更新原 SDD。原需求已验收收口，本轮新增能力或改变已验收的行为时新建 SDD。补正历史文案或补录当时的证据，写入原 SDD 的更正记录。
- 旧方案引用写入 `metadata.previousSpecs[]`。必填 `source`（仓库相对路径或共享 HTTP(S) 链接）和 `summary`（沿用或变更什么）。有旧条目或可追溯版本时添 `recordIds` 或完整 `commit`。旧编号在旧方案内查找。需要关联旧证据时，先在本轮事实源登记来源，再关联本轮证据编号。
- 制定方案前重新核对当前仓库、分支、提交和目标环境，按影响范围核对代码、接口、迁移、配置和验收证据。只沿用本轮仍适用的旧结论。缺少证据的事项标「待核实」。

## 控制上下文

优先用任务 PLAN/API/DATA 的 ID 取数，不加载整份 HTML、JSON、日志或所有参考文件：

```bash
html-sdd context <JSON> PLAN-001 --role executor --full --json
# 默认 8 条关联摘要、12000 字符预算（不是精确 Token）
# 按返回 nextOffset 继续：--offset N；需要时 --limit 1..48 --max-chars N
html-sdd check <JSON>
html-sdd render <JSON> --output <HTML>
```

默认生成 Vue 版。请用浏览器直接打开本地 HTML 文件。HTTP 和 HTTPS 下页面会提示改用本地文件。Vue 版需联网加载 Vue，无法联网时给 `render` 加 `--template classic`。

公共参数/规则可用 `definitions.fields/rules` 和本地 `$ref` 复用；`reuse` 先预览再生成候选，展开等价后替换。

`--full` 自动解析公共引用，只展开目标记录，执行前按相关 ID 读取适用完整契约。分页摘要不是全部合同；检查省略计数，依赖/阻塞/证据也有数量上限，按 ID 补读。预算不足会报错，不得当成无阻塞。通常无需读取生成器和页面源码；只检查本次变更。

验证输出优先摘要，失败再读必要片段。已有 Playwright 会话可运行 `html-sdd browser-check <脚本.js> --session <会话名>`；需预装 playwright-cli，打开会话和调用命令必须在同一工作目录。日志在 `output/playwright/`，须 Git 忽略，不放敏感值。

## 字段级变更

新增接口和新增数据表只填写整项的 `changeType`，省略字段和字段引用上重复的 `changeStatus: "新增"`。存量接口和表只给实际变化的字段填 `changeStatus`（新增、修改、删除）。已有重复标记可用 `reuse <JSON> --output <候选JSON>` 清理。删除只保留原字段名、必要的请求位置与状态，更新示例和 DDL 时按当前契约填写。共享参数将状态写在本次使用的 `$ref` 同级。普通 `render` 直接标色。需要比较旧值时才用 `diff <基线JSON> <当前JSON> --json`。

新增表的 DDL 已完整记录列名、类型、可空性、默认值和说明时，省略重复的 `columns`。列快照有 DDL 未覆盖的信息，或本轮需要列级比对时，保留它。

接口的逐字重复说明可用 `reuse <JSON> --output <候选JSON>` 提取到公共定义。补充说明仍写在 `notes`，调用约束仍写在 `rules`。只调整排版时用 `html-sdd format <JSON> --output <候选JSON>` 生成可读的紧凑 JSON，核对后替换。

## 盘点整个需求

用户问「整个需求还剩哪些」「还有什么没做完」或「离上线还差什么」时，先运行 `html-sdd summary <JSON> --json`，再用 `context` 按 ID 补查。默认 Vue 的「剩余事项」与摘要使用同一份盘点结果，更新事实源后重新渲染。空板块要区分不涉及、待补充和尚未判断。旧版 CLI 没有 `summary` 时，用 Python 或 jq 提取下列字段。参数不确定时运行 `html-sdd <子命令> --help`。

1. 读取全部 `plans` 的模块、任务编号、状态、进展和阻塞，按模块列出剩余工作。已取消的任务单列。
2. 对照全部 `requirements[].acceptance`、`metadata.readiness.blockingItems` 和未关闭的 `questions`。按关联核对接口、数据表和上线配置，补上排期里漏记的部署、DDL 执行和验收事项。同一缺口只报一次。
3. 对证据有疑问的条目，用 `html-sdd context <JSON> <ID> --role owner --full` 补查。按证据区分本地、测试和生产。证据不足标「待核实」。汇报写清剩余事项、阻塞、处理人和下一步；处理人缺失时标「待安排」。

## 协作和阅读约定

支持单 Agent；有可独立任务且环境支持时再多 Agent，服从用户选择。一份需求一个负责人；每项任务有主审核人/主执行人，可各自协作，并行执行的 `ownerPaths` 不重叠。负责人核实所有未取消的子需求，确认范围、排期、验收例子和适用合同，关闭编码阻塞。整单可编码时设 `metadata.readiness.codingReady=true`，`blockingItems` 填空数组，并运行 `check`。实际验收通过后再关联已验证证据。对用户默认 300 字内，说明目标、进行中、下一步、完成项和问题。

多 Agent 内部交接以 PLAN 编号为准。审核人核对当前实现、范围、待决事项和验收条件。执行人领取已分派且不受阻的任务，遇到契约变化或环境阻塞时交回负责人。回报任务编号、状态、完成内容、验证证据、改动路径、阻塞和下一步。

页面维持需求、排期、接口、数据表、架构设计、上线需要配置六类入口；左右布局单项详情，排期全宽表格。冷白＋墨蓝，清晰字号；接口全 path 保留原生 Cmd+F。Mermaid 使用 `diagramEngine` 指定并保留图源回退。

设计页面或维护协作细则时，按需读取 [页面与协作规范](references/页面与协作规范.md)；不要每次全读。字段以已安装 CLI 对应 schema 为准，旧字段保持兼容。

## 变更与验收记录

过程草案、调研笔记和阶段实施计划按需放 `临时文件/`，由 Git 忽略。已确认的对接合同、发布文件和验收结论保留在共享交付物中。仅本机有草案时标「本机留存」。

记录规则默认生效。重要变更确认后追加 `变更记录/变更记录.md`，写日期、结论、原因、改前改后、影响、关联编号和验证。验收后在事实源的 `evidence[]` 登记编号、时间、环境、对象和结果。要留原件时，将脱敏文件放到 `证据/<编号>-<环境>-<验证事项>.<扩展名>`。同一编号有报告、截图等多份材料时，建立同名目录，把这些文件放在一起。多个环境或批次难定位时，用 `证据/索引.md` 记录编号、环境、日期或批次和相对路径。

两个归档目录首次使用时创建，均由 Git 忽略。共享事实源记录结论和可访问引用，仅本地有原件时标「本机留存」。缺证据写「待核实」。已有归档保留。没有授权不执行 DDL、线上配置、提交或推送。事实源、HTML 和日志不写凭据。

状态使用 `html-sdd statuses --section <板块>` 查询的短枚举，说明写 `statusNote`。init 默认严格模式；旧长句保留原文并待核实，不按关键词猜完成或颜色。各阶段状态与编码条件独立；修改字典须同步生成 Schema/规范并验证，不能在需求 JSON 中改颜色。

架构按主模块组织，每模块默认一份当前方案及必要图；复用稳定ID，原位更新或合并被替代内容。查漏、讨论和实施批次不进入架构目录，整理时迁移关联，不改业务契约或推断实现状态。

页面与汇报用普通中文：先说结论，短句，一点一件事。少术语和缩写，必要时先解释；标题用业务动作或结果。进展写当前结果和下一步，验证写环境、对象和结果。长说明拆成短条目，重复细节留在本地归档。接口字段/路径/枚举及业务限制保持精确，不能为简短删规则或夸大完成情况。

菜单名称与路径单独显示；类型/方法、变更类型和状态统一放在底部标签行，保持相同顺序、字号和间距，不遮挡名称。
