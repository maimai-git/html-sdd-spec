# HTML SDD Spec

当用户说“用 HTML SDD 实现这个需求”或“用 HTML SDD 先梳理这个项目”时使用本 Skill。用户通常只需提供一句需求描述；不要先要求用户列接口、列数据表、填写排期表头或编写负责人/审核人/执行人提示词。

## 目标

- 先建立当前版本基线，再提出本次方案；已实现、文件已存在但未执行、提案和待核实必须分开写。
- 让产品和技术在同一份页面上对齐：需求、排期、接口、数据表、架构设计、上线需要配置。
- 让 AI 后续按稳定 ID 读取必要内容，不把整份 HTML 反复塞进上下文。
- 让排期和证据可以持续更新，直到开发、测试、上线和验收收口。

## 默认动作

1. 读取项目规则、仓库、分支、完整提交 SHA、检查时间、时区和工作树状态。
2. 只读检查路由/控制器、服务、持久化、migration、配置、测试和已有文档；前端可以看，但本 Skill 默认不改前端。
3. 在项目根目录创建或更新 `html-sdd-spec/<开发需求目录>/`：
   - `方案事实源.json`：唯一可编辑的机器事实源；
   - `方案对齐.html`：由 JSON 渲染的离线阅读页面；
   - `使用说明.md`、`变更记录/`、`证据索引/`：按项目需要补充。
4. 用稳定 ID（`REQ-*`、`PLAN-*`、`API-*`、`DATA-*`、`ARCH-*`、`CFG-*`、`EVID-*`）串起需求、排期、接口、表、架构、配置和证据。
5. 只有会改变业务行为、权限、接口/表设计、迁移、外部接入或执行授权的问题才反问用户；其余技术细节根据代码证据处理，并标注假设或待核实。
6. 运行 `check`、`render`，再按需运行 `diff`；不要直接手改生成后的 HTML。

## 六个阅读入口

- **需求**：目标、范围、验收标准和关联记录；
- **排期**：宽屏整页表格，展示优先级、模块/主任务、关联需求、执行人、计划时间、状态、最新进度、备注、阻塞和详情；详情展开负责人、审核人、子任务、批次、预估和依赖。同一模块使用同一行色；
- **接口**：按业务分组，右侧一次只看一个接口；必须区分新增接口和存量接口变更，并展示当前代码现状、请求参数、返回参数、请求实例和响应实例；
- **数据表**：按业务分组，右侧一次只看一张表；必须区分新增、存量变更和复用，并展示表作用、当前状态、结构差异和 DDL 黑色文本框；
- **架构设计**：技术方案用结论、当前现状、实施步骤、影响范围、风险/待确认；架构图和时序图同时保留图源或文字降级说明；
- **上线需要配置**：环境变量、Apollo、DDL 和人工执行项只展示非敏感文本，不在页面中执行。

分类可以为空。未涉及写明“不适用”及原因，未梳理完成写“待补充”和问题；不要为了填满页面虚构接口、表或架构图。

## Agent 协作

默认自动选择单 Agent 或多 Agent：小改动、单模块和无接口/数据影响使用单 Agent；跨模块、接口和数据同时变化、可并行或需要独立复核时使用多 Agent。用户明确指定时服从用户。

- 一份 SDD 只有一个负责人 Agent，负责和用户对齐、维护事实源、分派和汇报；
- 每个 PLAN 有一个主审核人和一个主执行人，可增加协作审核人/执行人；并行执行必须填写不重叠的 `ownerPaths`；
- 顺序固定为：负责人建基线 → 审核人拆解并冻结契约 → 负责人确认 `codingReady` → 执行人开发/验证 → 审核人复核 → 负责人汇报；
- 每个 Agent 读取同一份 JSON，按 `requirementIds`、`related` 和 ID 精确取数；完成后回填 `progress`、`evidence`、`changedPaths`、`blocker` 和 `next`。

## 排期状态

`plans[].status` 只能使用固定枚举：

`待拆分`、`待确认`、`编码 READY`、`待开始`、`进行中`、`待接入`、`待执行`、`待复核`、`待验收`、`阻塞`、`已完成`、`已取消`

页面为这些状态统一颜色；`plans[].note` 写补充说明，`blocker` 写阻塞原因。没有新证据时保留原状态并汇报“无变化”，不能凭感觉标记完成。

## 方案变更和门禁

- 开发或验证中发现接口、数据、架构、配置、验收或排期变化时，先改 `方案事实源.json`，再运行 `check`、`render`、`diff`；
- 原方案不再成立时，把受影响 PLAN 改为“待复核”，将 `metadata.readiness.codingReady` 改为 `false`，重新确认后才能交给执行人；
- `codingReady=true` 前，适用的接口/表/架构/配置必须关联到需求，验收项必须有可追踪证据；不适用的分类要明确说明；
- migration 文件不等于数据库已执行，外部平台接入不等于真实链路已验收；缺证据就写“待核实”。

## 命令

在仓库根目录使用：

```bash
python3 -m html_sdd check html-sdd-spec/<开发需求目录>/方案事实源.json
python3 -m html_sdd render html-sdd-spec/<开发需求目录>/方案事实源.json \
  --output html-sdd-spec/<开发需求目录>/方案对齐.html
python3 -m html_sdd diff before.json after.json --json
```

不要执行 DDL、修改线上配置、提交或推送，除非用户明确授权。不要把 Token、密码、Cookie、私钥、连接串或真实密钥写入 JSON、HTML、示例或日志。负责人对用户的汇报保持简短，默认 300 字以内，固定五行：阶段目标、进行中、下阶段规划目标、已完成任务/需求、存在问题。
